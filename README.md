# Mandelbrot in Bend 2

A small, native **Bend 2** experiment: render a fractal, zoom into it, and compare
sequential computation with explicit CPU fork–join parallelism. All rendering,
argument parsing, and image writing are Bend; Python is only used for optional
tests and benchmarks. No third-party project dependencies.

## Quick start

Requires macOS or Linux, `make`, `curl`, and clang 14+ for native compilation.
Python 3.10+ is needed for the integration tests and benchmark.

```sh
make setup       # download a checksum-verified compiler into .tools/ only
make image       # quick preview: output/mandelbrot.ppm (+ PNG on macOS)
make hq          # detailed zoom: 3840x2560, 3000 iterations, 16 samples/pixel
```

On macOS, `make image` also creates **`output/mandelbrot.png`** using the built-in
`sips` utility. To view it:

```sh
open output/mandelbrot.png
open output/zoom-hq.png       # generated by make hq
```

PPM (P6) is an uncompressed image format: a short text header followed by raw RGB
bytes. Keeping the format simple lets us concentrate on Bend rather than image
libraries. On other platforms, open the PPM with a compatible image viewer.

The toolchain is pinned to official **Bend 2.0.37**, published **13 October 2026**.
`scripts/setup.sh` checks the SHA-256 digest published with the release before
extracting it. Nothing is installed globally. The first native build may take a
few seconds; subsequent runs execute the binary directly.

## Experiment

```sh
# width height iterations output mode [center_x center_y horizontal_span [samples]]
./build/mandelbrot --threads 8 960 640 300 output/example.ppm parallel

# Same image, with no render forks.
./build/mandelbrot --threads 1 960 640 300 output/sequential.ppm sequential

# Zoom into a region near the Seahorse Valley.
./build/mandelbrot --threads 8 960 640 800 output/zoom.ppm parallel -0.7435 0.1314 0.012

# High-detail zoom with 4x4 subpixel anti-aliasing (not an upscaled preview).
./build/mandelbrot --threads 8 3840 2560 3000 output/zoom-hq.ppm parallel -0.7435 0.1314 0.012 4

# Optional macOS conversion.
sips -s format png output/zoom.ppm --out output/zoom.png

# Compare output byte-for-byte (use the same view and iteration count).
cmp output/example.ppm output/sequential.ppm

./build/mandelbrot --help
```

Create the output's parent directory yourself if it does not exist. With no
application arguments, the binary uses `960 640 300 mandelbrot.ppm parallel`.
Place runtime options such as `--threads 8` **before** application arguments.
`THREADS` can also be changed for the Make targets: `make image THREADS=4`.

- **Iterations:** more work per pixel, more detail near the fractal boundary.
- **Centre:** the complex coordinate at the image centre.
- **Span:** the horizontal width of the view; smaller means more zoom.
- **Aspect ratio:** automatically preserves equal scale on both axes.
- **Samples:** grid size 1–4; `4` traces 16 independent orbits per pixel and
  averages their colours. Defaults to 1; specified after the view coordinates.
- **Colour:** continuous logarithmic escape-time shading instead of hard bands.
- **Limits:** dimensions 1–8192, at most 16,777,216 pixels, iterations 1–10,000;
  coordinates and span must be finite with absolute value <= 1,000,000, span > 0.
- **Precision:** Bend currently provides `F32`, so deep zooms eventually lose
  detail. Increasing iterations cannot recover coordinate precision.

## What the code does

Each pixel represents a complex number `c = cx + cy*i`. Starting at `z = 0`,
repeat `z = z*z + c`, stopping when `|z|² > 4` or the iteration budget runs out.
In real arithmetic this is:

```text
next_x = zx*zx - zy*zy + cx
next_y = 2*zx*zy + cy
```

Escaping points get a continuous cosine palette based on the smoothed escape time
`steps + 1 - log2(log(|z|))`, avoiding the old integer-iteration bands. Points that
have **not escaped within the budget** are black: this is an approximation, not
a mathematical proof of membership. With one sample, pixels are sampled at their
centres; higher settings sample an evenly spaced subpixel grid and average the
RGB values. Positive imaginary values are at the top of the image.

The HQ preset calculates **157,286,400 sample orbits**, each with up to 3,000
iterations. It increases actual spatial sampling rather than resizing the old
image. This run took **28.079 seconds** to render with 8 workers and about **475 MB**
peak resident memory. Very fine boundary features remain limited by `F32`;
supersampling does not turn this into an arbitrary-precision renderer.

### Files to explore

- **`mandelbrot.bend`** — start here:
  - `orbit` / `escape`: the numerical rule; decreasing `Nat` fuel establishes termination.
  - `color`: change the palette here.
  - `sample` / `pixel` / `supersample`: screen-to-complex mapping and subpixel anti-aliasing.
  - `tile`: a sequential pixel loop using a reversed byte accumulator.
  - `render`: the parallel experiment; split contiguous pixel ranges in halves.
  - `write_pixels`: stream the result tree in row-major order.
- **`main.bend`** — CLI validation, timing, and PPM file output.
- **`tests.bend`** — ten runtime checks for known points and iteration boundaries.
- **`scripts/test_render.py`** — native integration tests and an independent F32 oracle.
- **`scripts/benchmark.py`** — alternating benchmark runs with image-equality checks.

### The parallel bit

Inside `render`, this is a real Bend 2 parallel let:

```text
a b = render(...) render(...)
Branch{a, b}
```

Parallel mode splits eight levels deep, producing 256 tiles. Sequential mode uses
zero levels, producing one tile. Both use the exact same pixel calculation.
The result is a tree of byte buffers: each task owns its output, with no shared
mutable array. File writes happen sequentially after rendering.

This is intentionally a baseline, not a tuned fractal engine. Some tiles contain
many quick-escaping pixels; others spend the full budget. Bend's scheduler favours
balanced work, so this imbalance can limit speedups. Try changing `8n` in
`main.bend` to `6n` or `10n`, then benchmark. More tasks are not always faster.

**This version targets the CPU, not the GPU.** It uses parallel lets but no GPU
`!` calls, so Metal/CUDA tooling isn't required. GPU rendering is a good next
experiment, once the CPU behaviour is familiar.

## Test and benchmark

```sh
make test
make bench                  # one warm-up + five measured runs per mode
make bench THREADS=4
make bench-hq               # zoom workload: 3000 iterations, 16 samples, three runs/mode
python3 scripts/benchmark.py --width 1200 --height 800 --iterations 500 --repeat 7
```

Tests cover known bounded/escaping points, escape on the final iteration,
non-power-of-two images, images smaller than the task count, custom views,
invalid input, output failures, and identical sequential/parallel images.
All subpixel grid sizes are tested against an independent F32 reference.

The benchmark alternates execution order, validates every image hash, and reports
median **render + pixel-buffer allocation** time. It excludes process startup
and file IO, and has millisecond resolution. Each run is a fresh process.

The updated HQ benchmark at 960×640 / 3,000 iterations / 16 samples per pixel
measured **9,544 ms sequential vs 1,664 ms parallel with 8 workers** (5.74×),
using the Seahorse Valley view and three measured runs per mode. Every output
was byte-identical. This is a local result, not a general performance guarantee;
rerun on your own machine.

The Bend compiler checks types and termination. Its `ALL PROOFS CHECK` message
here does **not** mean floating-point correctness or full Mandelbrot membership
has been formally proven. There are no project-specific laws in this version;
the numerical checks are executable tests.
